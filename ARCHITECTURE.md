# ESP32 Serial Analyzer
## Architecture & Functionality — Version 0.3

## 1. Назначение проекта

ESP32 Serial Analyzer — desktop-приложение для Ubuntu, предназначенное для взаимодействия с микроконтроллерами ESP32 через последовательный интерфейс UART.

Программа обеспечивает:

- Приём данных от ESP32.
- Отображение логов Zephyr RTOS в структурированном виде.
- Цветовое выделение уровней логирования.
- Фильтрацию сообщений.
- Передачу команд на устройство.
- Сохранение полученных логов в файлы.
- Открытие ранее сохранённых журналов для последующего просмотра и анализа.

Основная задача приложения — предоставить удобный инструмент разработки и отладки прошивок ESP32.

### Целевая платформа

- ОС: Ubuntu Linux.
- Микроконтроллер: ESP32.
- RTOS: Zephyr RTOS 4.5.0.
- Интерфейс связи: UART / USB Serial.
- Типичные устройства: `/dev/ttyACM*`.

## 4. Архитектура приложения

Приложение разделено на три основных логических уровня:

1. Core — работа с последовательным портом и файлами.
2. Parsers — обработка и структурирование входящих данных.
3. GUI — отображение информации и управление приложением.

### Общая схема обработки данных

```text
              ESP32
                |
                | UART / USB Serial
                |
                v
        +------------------+
        |   SerialWorker   |
        |     QThread      |
        +------------------+
                |
                | bytes
                v
        +------------------+
        |    LogParser     |
        +------------------+
                |
                | ParsedMessage
                v
        +------------------+
        |    MainWindow    |
        +------------------+
                |
          +-----+------+
          |            |
          v            v
      QTableWidget  LogStorage
          |            |
          v            v
       Display      JSONL File
```

`SerialWorker` принимает данные из UART и передаёт их главному потоку через Qt Signal.

`LogParser` преобразует последовательность байтов в отдельные сообщения.

`MainWindow` получает структурированные сообщения и отвечает за их отображение.

`LogStorage` используется для записи сообщений в файл, если пользователь активировал журналирование.

Таким образом, файловое сохранение не является обязательным условием работы Serial Monitor.

## 5. Работа с последовательным портом

За взаимодействие с ESP32 отвечает класс `SerialWorker`, расположенный в:

```text
core/serial_worker.py
```

Класс реализован на основе `QThread`.

### Основные функции

- Открытие последовательного порта.
- Настройка скорости передачи.
- Приём данных.
- Передача данных на ESP32.
- Контроль состояния соединения.
- Корректное завершение работы потока.

Используется библиотека pySerial.

Типичные параметры подключения:

```python
baudrate = 115200
timeout = 0.1
write_timeout = 1
```

### Сигналы Qt

Для взаимодействия с главным окном используются сигналы:

```python
data_received = Signal(bytes)

connection_status = Signal(bool, str)
```

`data_received` передаёт принятые байты.

`connection_status` сообщает об изменении состояния подключения.

### Передача команд

Пользователь может вводить команды в специальное поле интерфейса.

Перед отправкой текст кодируется в UTF-8.

По умолчанию к команде добавляется символ новой строки:

```python
data += b"\n"
```

Важно: наличие UART-консоли в конфигурации Zephyr само по себе не гарантирует обработку пользовательских команд. Для этого прошивка должна содержать Zephyr Shell или собственный обработчик входящих данных UART.

## 6. Обработка логов

Обработка входящих данных выполняется модулем:

```text
parsers/log_parser.py
```

Класс `LogParser` принимает байтовые данные и формирует из них отдельные сообщения.

### Основные функции парсера

- Буферизация входящих байтов.
- Формирование строк по символу `\n`.
- Обработка неполных UART-пакетов.
- Декодирование UTF-8.
- Удаление ANSI escape-последовательностей.
- Распознавание стандартного формата логов Zephyr.
- Извлечение структурированных полей.

### Пример входящего сообщения

```text
[00:09:24.883,000] <wrn> adc_esp32: ADC reading is uncompensated
```

### Результат обработки

Парсер формирует объект `ParsedMessage`:

```python
@dataclass
class ParsedMessage:

    text: str

    timestamp: Optional[str] = None

    level: Optional[str] = None

    module: Optional[str] = None

    message: Optional[str] = None
```

Поля:

| Поле | Назначение |
|---|---|
| `text` | Исходный текст после удаления ANSI-последовательностей |
| `timestamp` | Временная метка |
| `level` | Уровень логирования |
| `module` | Имя модуля |
| `message` | Текст сообщения |

Если сообщение не соответствует известному формату Zephyr, оно сохраняется как обычный текст с уровнем `OTHER`.

### ANSI-форматирование

Zephyr может передавать управляющие ANSI-последовательности, например:

```text
ESC[1;33m
ESC[0m
```

Они используются для форматирования текста в терминале.

Парсер удаляет эти последовательности, поскольку цветовое оформление выполняется непосредственно приложением.

## 7. Пользовательский интерфейс

Главное окно реализовано в:

```text
gui/main_window.py
```

Для отображения сообщений используется `QTableWidget`.

### Таблица логов

Основные столбцы:

| Столбец | Содержание |
|---|---|
| TIME | Временная метка |
| LEVEL | Уровень логирования |
| MODULE | Модуль Zephyr |
| MESSAGE | Текст сообщения |

### Цветовое оформление

Для разных уровней логирования используются отдельные цвета:

| Уровень | Цвет |
|---|---|
| ERR | Красный |
| WRN | Жёлтый |
| INF | Зелёный |
| DBG | Серый |
| OTHER | Светло-серый |

### Фильтрация

Доступны фильтры:

- ERR
- WRN
- INF
- DBG
- OTHER

Фильтрация выполняется скрытием строк таблицы.

Исходные сообщения при этом не удаляются.

### Ограничение истории

Для обычного Live-режима установлено ограничение:

```python
MAX_ROWS = 5000
```

При превышении лимита самые старые строки удаляются из таблицы.

Это позволяет ограничить использование оперативной памяти при длительном мониторинге.

Ограничение интерфейса не распространяется на автоматическую запись в файл.

## 8. Сохранение логов

За файловое хранение отвечает:

```text
core/log_storage.py
```

Класс `LogStorage` реализует:

- Создание каталога `logs/`.
- Создание новых файлов журналов.
- Запись сообщений в JSONL.
- Закрытие файлов.
- Загрузку ранее сохранённых журналов.
- Сохранение набора записей в выбранный файл.

### Формат JSON Lines

Используется формат JSONL.

Каждая строка файла представляет собой отдельный JSON-объект.

Пример:

```json
{"timestamp":"00:09:24.883,000","level":"wrn","module":"adc_esp32","message":"ADC reading is uncompensated","text":"[00:09:24.883,000] <wrn> adc_esp32: ADC reading is uncompensated"}
{"timestamp":"00:09:25.120,000","level":"inf","module":"main","message":"System initialized","text":"[00:09:25.120,000] <inf> main: System initialized"}
```

### Преимущества JSONL

- Каждое сообщение хранится независимо.
- Структурированные поля легко восстанавливаются.
- Файл можно читать построчно.
- Формат подходит для обработки большими объёмами данных.
- Возможность расширения структуры без изменения общей концепции хранения.

### Автоматическое именование файлов

При запуске записи имя файла формируется автоматически.

Пример:

```text
esp32_2026-11-23_14-45-30.jsonl
```

Файлы создаются в каталоге:

```text
debug_console/logs/
```

Для создания используется режим открытия `x`, который предотвращает случайную перезапись существующего файла.

### Управление записью

В интерфейсе предусмотрены:

**Start Logging**

Создаёт новый файл и включает автоматическую запись принятых сообщений.

**Stop Logging**

Останавливает запись и закрывает файл.

**Logging: ON / OFF**

Отображает состояние файлового журналирования.

Во время активной записи каждое разобранное сообщение передаётся в `LogStorage`.

Для повышения надёжности после каждой записи вызывается `flush()`.

### Независимость от интерфейса

Запись в файл не зависит от количества строк, отображаемых в таблице.

Даже если старые строки удаляются из `QTableWidget` после достижения лимита 5000 сообщений, они остаются в журнале на диске.

## 9. Открытие сохранённых журналов

Для просмотра ранее сохранённых журналов предусмотрена функция:

**Open Log**

Пользователь выбирает файл JSONL через стандартный диалог открытия файлов.

Программа:

1. Загружает записи из файла.
2. Восстанавливает объекты `ParsedMessage`.
3. Очищает текущую таблицу.
4. Заполняет таблицу сохранёнными сообщениями.
5. Применяет цветовое оформление.
6. Применяет текущие фильтры уровней.

Таким образом, сохранённые журналы отображаются в том же формате, что и сообщения, полученные непосредственно от ESP32.

### Просмотр больших файлов

При загрузке сохранённого журнала ограничение `MAX_ROWS` временно отключается.

Это позволяет просматривать журналы, содержащие более 5000 сообщений.

### Возврат к Live-режиму

Для возвращения к мониторингу предусмотрена кнопка:

**Return to Live**

При её нажатии:

- Таблица очищается.
- Режим просмотра файла завершается.
- Если UART подключён, снова отображаются новые сообщения устройства.

Если UART остаётся подключённым во время просмотра файла, приём данных продолжается, но сообщения не добавляются в таблицу.

Счётчик RX продолжает обновляться.

### Защита от смешивания данных

Если файловое журналирование активно, открытие другого журнала блокируется до остановки записи.

Если UART подключён, перед открытием файла пользователь получает предупреждение.

Оригинальный файл журнала при просмотре не изменяется.

## 10. Сохранение текущей истории

Дополнительно предусмотрена функция:

**Save Log As...**

Она позволяет сохранить текущие записи таблицы в выбранный JSONL-файл.

В отличие от автоматического журналирования, эта функция сохраняет именно текущую историю, представленную в таблице.

Следовательно, результат может отличаться от полного автоматического журнала, если:

- Было превышено ограничение в 5000 строк.
- Некоторые уровни сообщений скрыты фильтрами.

Автоматическая запись предназначена для сохранения полного потока разобранных сообщений, а `Save Log As...` — для сохранения текущей истории отображения.

## 11. Основные сценарии использования

### Сценарий A. Мониторинг ESP32

1. Запустить приложение.
2. Выбрать последовательный порт.
3. Установить скорость передачи.
4. Нажать Connect.
5. Получать сообщения от ESP32.
6. Использовать фильтры для анализа логов.

### Сценарий B. Сохранение отладочной сессии

1. Подключиться к ESP32.
2. Нажать Start Logging.
3. Выполнять отладку прошивки.
4. Получать и автоматически сохранять сообщения.
5. Нажать Stop Logging.
6. Получить готовый JSONL-файл в каталоге `logs/`.

### Сценарий C. Просмотр ранее сохранённого журнала

1. Нажать Open Log.
2. Выбрать JSONL-файл.
3. Просмотреть сообщения.
4. Использовать фильтры уровней.
5. Нажать Return to Live для возвращения к мониторингу.

### Сценарий D. Передача команды

1. Подключиться к ESP32.
2. Ввести команду в поле ввода.
3. При необходимости включить добавление символа новой строки.
4. Нажать SEND или Enter.
5. Команда передаётся через UART.

- Анализ ошибок и предупреждений.

Формат JSONL является основным форматом сохранения и открытия собственных журналов приложения.

В текущей архитектуре разделены:

- Работа с последовательным интерфейсом.

- Отображение логов.
